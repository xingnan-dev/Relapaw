# Relapaw 真实产品首发差距审计

状态：**已完成**  
版本：1.0  
审计日期：2026-10-16  
审计基准：[真实产品首发契约](LAUNCH_PRODUCT_SCOPE.md)  
审计范围：当前仓库中的前端、后端、数据库迁移、自动测试、部署占位与既有验收证据  

## 1. 结论

当前版本已经具备首发产品最难伪造的**领域闭环**：结构化 Episode、Observation 与 Owner Interpretation 分离、人工 Safety Check、Timeline、复评、观察计划、长期记忆人工决定、量化 Baseline 与 Evidence lineage 均有实现和测试。

但当前版本仍是**可信的单机演示/开发版本，不是可邀请真实用户的产品**。真实首发存在四个发布阻断：

1. **没有账号、认证、授权与数据归属**：数据库没有 User/Account，Pet 没有 `user_id`，所有资源可按整数 ID 读取或修改；
2. **没有隐私与数据权利闭环**：没有条款同意记录、正式隐私说明、数据导出、账号删除或保存期限实现；
3. **未关闭未获资格的 AI 入口**：Episode 详情仍直接渲染 `UnderstandingPanel`，生产 API 也没有资格开关；
4. **没有生产运行基线**：Docker Compose 明确只是占位，仍以 SQLite 为默认数据库，没有正式部署、监控、备份恢复或生产环境隔离证据。

因此首发判断为：

> **外部多人 Beta NO-GO：不得邀请真实用户共用当前系统。** 当前本地比赛/演示版本可以继续；只有转向外部多人 Beta 时，才需要完成 P0-1 至 P0-4 四个实施批次。

该判断不否定现有 Phase 0–3、Evaluation 或 UI/UX 验收；它们解决的是领域能力、质量和演示完整性，不等于真实用户发布准备度。

## 2. 审计方法与状态定义

每项首发要求使用以下状态：

- **完成**：已有端到端实现、用户入口和足够测试证据；
- **部分完成**：核心实现存在，但缺少首发要求中的入口、状态、隔离或验收；
- **缺失**：当前仓库没有对应产品能力；
- **阻断**：现状与已冻结的首发契约冲突，发布前必须改变；
- **待验证**：可能已有局部实现或历史人工结论，但缺少本轮可复核的生产证据。

优先级定义：

- **P0**：受邀 Beta 前必须完成；
- **P1**：可在 Beta 中迭代，但不得以虚假入口或承诺出现；
- **P2**：已明确不属于首发。

## 4. 已完成、可复用的首发资产

以下能力不应重写，只需在加入账号边界后做授权与回归：

- Episode、Observation、Owner Interpretation、SafetyCheck 与 EvidenceReference 数据语义；
- Timeline 的分页、时间/类型/计划筛选、详情、编辑和错误状态；
- Follow-up 的安排、取消、完成、五种结果和历史保护；
- Observation Plan 的最小创建、完成、取消和 Episode 关联；
- Analysis 的 Safety 前置阻断、失败审计、Evidence 与 Uncertainty 契约；
- Memory Candidate 的显式纳入、撤回、stale 与追加式决定历史；
- Baseline 的 7/30/90/all、样本门槛、趋势规则、重算、stale 与字段级 lineage；
- 响应式应用壳、四个一级入口、基础可访问性与视觉状态语言；
- Alembic 迁移框架、统一 API 错误结构和服务端 Secret 边界。

这些能力的“已有”不代表自动满足多用户授权、隐私合规或生产运行要求。

## 5. 冻结的 P0 交付清单

### P0-1：账号、租户边界与宠物切换（外部多人 Beta 前启用）

目标：把单一共享数据空间改造成每位受邀用户的私有空间。

必须交付：

- 身份方案与威胁模型；
- User/Account 数据边界和迁移；
- 注册或邀请、登录、退出、会话恢复和撤销；
- Pet 归属及所有资源的授权链；
- 当前宠物选择器和多宠无串数据；
- 两用户 IDOR 自动测试；
- 审计日志只记录必要元数据，不保存完整私密正文。

退出条件：A-01 至 A-04 全部通过，且现有 183 项自动测试无回退。

### P0-2：隐私与数据生命周期

目标：让真实用户知道数据如何使用，并能带走或删除自己的数据。

必须交付：

- 数据清单、用途、保存期限和第三方处理清单；
- 服务条款、隐私说明及版本化同意记录；
- 数据导出；
- 账号删除与关联数据生命周期；
- Episode 删除与不可变审计之间的正式产品/技术决定；
- 备份中的删除与到期策略；
- 产品内真实入口和完成反馈。

退出条件：A-05 至 A-07、R-06 全部通过，并完成隐私审核与删除演练。

### P0-3：首发能力收口与安全开关

目标：确保真实用户只能看到已承诺、已资格化的能力。

必须交付：

- AI Understanding 服务端资格开关，默认关闭；
- 前端能力发现或构建配置，关闭时不渲染入口和历史候选死路；
- 直接调用分析 API 的拒绝行为；
- Safety 阻断回归；
- 资料编辑、宠物切换和真实隐私入口；
- 全站交互元素与营销文案审计；
- 网络错误、会话过期和提交失败保态测试。

退出条件：AI-01、X-01、R-12、Q-01 通过；当前 `NOT_QUALIFIED` 结论在代码配置、UI 和材料三处一致。

### P0-4：生产部署与运营准备

目标：让 Beta 不依赖开发者电脑和临时终端，并可发现、恢复和暂停故障。

必须交付：

- 托管架构、PostgreSQL 与生产迁移；
- staging/production 隔离、HTTPS、CORS 和 Secret 管理；
- 结构化日志、错误监控、健康检查和告警；
- 自动备份与恢复演练；
- 最小 CI/CD、部署版本标识和回滚流程；
- 支持渠道、事件响应、暂停邀请和状态沟通机制；
- staging 核心路径与浏览器/无障碍回归。

退出条件：O-01 至 O-06、Q-02 至 Q-04 通过，才允许创建真实用户 Release Candidate。

## 6. P1 清单

以下能力不阻塞首批邀请，但必须保持无虚假入口：

- 更丰富的宠物档案与头像；
- 自定义提醒渠道和更完整的观察计划编辑；
- Timeline 搜索、更多筛选和事实摘要导出；
- 人工 Baseline 创建/编辑；
- 匿名产品分析与反馈面板；
- 兽医沟通事实摘要；
- 图片资源压缩和进一步性能优化；
- 已通过资格门禁后的 AI Understanding 与长期记忆候选。

## 7. 不进入交付清单的内容

以下能力继续保持 P2/赛后，不得混入首发实施批次：

- 医疗诊断、分诊、治疗或用药建议；
- RAG、Agent、多模态识别；
- Pet↔Pet 自动关系推断；
- 组织账号、兽医端与多人协作；
- 社区、排行榜、电商、保险或问诊交易；
- 原生移动应用、穿戴设备或完整离线模式。

## 8. 实施顺序与依赖

```text
P0-1 账号与数据归属
  → P0-2 隐私与数据生命周期
  → P0-3 能力收口与 AI 默认关闭
  → P0-4 生产部署与运营准备
  → Release Candidate 总验收
  → 第一批真实用户邀请
```

P0-3 的 AI 默认关闭可以与 P0-1 的后端设计并行准备，但首发总验收必须在 P0-1、P0-2 完成后进行。生产部署不能先承载真实数据再补授权或隐私能力。

## 9. 下一步

P0-1 候选设计保留在 [账号、身份与租户边界架构](P0_1_IDENTITY_TENANCY_ARCHITECTURE.md)，但当前没有域名、正式发信邮箱或外部多人 Beta 计划，因此暂缓实施，也不继续该方案的实现前 Review。

未来触发外部多人 Beta 时，该技术方案需要重新确认：

1. 使用托管身份服务还是自建凭据；
2. Web 会话采用 HttpOnly Cookie 还是其他机制；
3. 现有无归属数据如何迁移、归档或仅保留在演示环境；
4. 每类资源如何从当前用户走完整授权链；
5. 账号删除、审计保留和备份删除如何协调；
6. staging、demo 与 production 如何彻底隔离。

当前发布形态已经冻结在 [比赛与演示版本发布形态](DEMO_RELEASE_PROFILE.md)：以本地可重复演示为主，只使用合成数据；受控线上预览为可选，外部多人 Beta 暂缓。下一步编写演示运行包的文件级实施计划；无账号版本不得公开承载多人真实数据。
