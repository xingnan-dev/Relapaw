# Relapaw 真实产品首发契约

状态：**已冻结**  
版本：1.0  
冻结日期：2026-10-16  
适用版本：首个面向真实用户的受邀 Beta  

当前实现与本契约的逐项映射、发布阻断和 P0 交付批次见 [真实产品首发差距审计](LAUNCH_GAP_AUDIT.md)。

## 1. 决策摘要

Relapaw 的第一次真实发布不是“宠物诊断 AI”，也不是功能齐全的宠物健康平台。首发产品是一个面向宠物主人的、可长期使用的行为观察与复评工具：帮助用户把事实与自己的理解分开记录，在时间线上回看变化，按计划再次观察，并在样本足够时查看这只宠物自身的行为基线。

首发形态冻结为：

- **发布方式**：小规模受邀 Beta，使用真实账号、真实宠物资料和真实记录；不是只供评委观看的演示环境。
- **首要用户**：希望理解宠物近期行为变化、愿意持续记录和复评的成年宠物主人。
- **核心任务**：当用户注意到一件值得留意的事时，在几分钟内完成一条有安全边界、可回看、可复评的记录。
- **核心承诺**：先保存“发生了什么”，再保存“我如何理解”；让后续判断能回到原始记录与时间，而不是替宠物下结论。
- **安全定位**：Relapaw 不诊断、不提供治疗或用药建议、不替代兽医。出现危险信号时，产品停止行为解释并持续提示联系兽医。
- **AI 定位**：当前 `qwen/qwen3.8-flash + text-understanding/v5-grounded-claims` 资格结论为 `NOT_QUALIFIED`。AI 文本理解不属于首发核心路径、默认关闭且不得作为首发宣传承诺。只有新的模型组合通过既定 Evaluation 与 Safety 门禁后，才能通过范围变更纳入 Beta。

## 2. 用户、场景与首发价值

### 2.1 目标用户

首发只服务一种主角色：**为一只或多只自有宠物负责日常照护的成年主人**。

用户需要满足至少一种动机：

1. 最近观察到宠物行为变化，想系统记录而不是凭一次印象判断；
2. 想在若干天后回来复评“改善、持续、加重或出现新情况”；
3. 想建立这只宠物自己的长期基线，并查看结论来自哪些记录；
4. 希望在与兽医沟通前整理事实时间线，但不把产品当作诊断工具。

### 2.2 不作为首发主用户

- 兽医、兽医机构或专业行为师的临床工作流；
- 救助机构、繁育机构、宠物店等组织型多成员协作；
- 未成年人独立使用；
- 只想上传照片或视频后立即获得“宠物在想什么”的用户；
- 需要急诊分诊、疾病诊断、处方或用药建议的用户。

### 2.3 首发需要验证的产品假设

首发只验证以下三件事：

1. 用户能理解并愿意使用 Observation 与 Owner Interpretation 的分离记录方式；
2. 用户会在记录后安排并完成复评，而不是只做一次性日记；
3. 来源透明、样本量明确的个体基线，比伪精确的情绪或健康评分更能帮助用户理解变化。

## 3. 首发成功时用户能完成什么

### 3.1 P0：必须随首发提供

| 能力 | 用户结果 | 首发边界 |
|---|---|---|
| 账号与会话 | 用户可进入自己的私有空间并安全退出 | 上线前必须具备；不得以共享匿名数据空间承载真实用户数据 |
| 宠物档案 | 创建宠物并在多只宠物间明确切换当前对象 | 支持基本身份资料；不做医疗档案系统 |
| 结构化记录 | 保存原始输入、发生时间、至少一条 Observation，可选 Owner Interpretation | 两类内容始终分字段、分标题保存 |
| 人工 Safety Check | 每次新记录和复评都检查危险信号 | 非 `NORMAL` 状态阻断任何模型解释，并持续显示联系兽医提示 |
| Timeline | 按宠物查看、展开、筛选、编辑和删除记录 | 编辑保留数据一致性；删除前说明影响范围并二次确认 |
| 复评 | 从原记录安排复评，到期后记录结果并回链原记录 | 结果至少覆盖持续、改善、加重、已消失、新情况 |
| 观察计划 | 创建一段有目标、有观察项的计划，并关联后续记录 | 支持完成或取消；不提供自动行为处方 |
| 个体基线 | 查看 7/30/90 天及全部历史的样本状态、指标和来源 | 样本不足必须明确显示；不得生成伪趋势或物种平均结论 |
| 长期记忆控制 | 用户明确纳入或撤回候选记忆 | 不自动把 AI 或普通记录写成长期事实；原始记录不被改写 |
| 数据权利 | 用户知道保存了什么，并可请求导出和删除账号数据 | 隐私说明、导出与删除路径在邀请真实用户前可用 |
| 基础可靠性 | 保存结果明确，失败时输入不丢失且可以重试 | 核心页面覆盖 loading、empty、error/retry 和离线/超时提示 |

### 3.2 P1：可在 Beta 内迭代，但不能阻塞首发

- 宠物档案编辑与头像；
- 更丰富的 Timeline 筛选、搜索和摘要；
- 自定义复评时间与提醒渠道；
- 更细的观察计划项目和完成进度；
- 基线的可视化表达优化；
- 经用户同意的匿名反馈与产品分析；
- 可下载的兽医沟通事实摘要，但其中不得包含自动诊断。

P1 功能未完成时，界面不得放置看似可用的入口、占位按钮或暗示已经提供该能力的文案。

### 3.3 条件能力：通过门禁后才可启用

AI 文本 Understanding 只有同时满足以下条件才可进入受邀 Beta：

1. 目标 Provider、模型、Prompt Contract 和评估数据集均有明确版本；
2. Evaluation 资格由 `NOT_QUALIFIED` 变为 `QUALIFIED`，且真实 Provider smoke test 通过；
3. 非 `NORMAL` Safety 状态能够确定性阻断调用；
4. 输出只包含带 Evidence、Uncertainty 和模型来源的候选 Claim；
5. 用户可逐条确认或拒绝，拒绝结果保留审计；
6. 模型内容不自动修改人工记录、Baseline 或长期记忆；
7. 产品文案不把候选解释表述为事实、诊断或宠物的第一人称表达。

未同时满足时，生产界面默认不展示 AI 分析入口；已有实现仅可用于内部评估环境。

## 4. 冻结的端到端用户流程

### 4.1 首次使用与建立档案

```text
接受邀请 / 注册登录
→ 阅读三项核心边界：事实与理解分开、长期变化需要记录、异常优先联系兽医
→ 同意服务条款与隐私说明
→ 创建第一只宠物
→ 进入 Today 真实空状态
→ 主动作是“开始第一条记录”
```

验收重点：允许用户暂时跳过宠物创建，但所有依赖宠物的数据页面必须显示真实空状态；不得填充伪造示例数据。

### 4.2 核心闭环：记录一件事

```text
Today 点击“开始记录”
→ 填写发生时间与原始描述
→ 分开填写 Observation 与 Owner Interpretation
→ 可选补充持续时间、次数、强度、地点、背景和观察计划
→ 完成人工 Safety Check
→ NORMAL：保存记录
→ NEED_MORE_INFO / ESCALATE_TO_VET：显示持续安全提示，阻断解释能力，用户仍可保存事实记录
→ 保存成功后进入该 Episode 详情
```

保存前必须让用户看清：哪些内容是事实、哪些是自己的理解，以及安全状态会带来什么结果。保存失败时保留当前输入。

### 4.3 回看、修订与删除

```text
Timeline
→ 按当前宠物读取记录
→ 筛选或找到目标 Episode
→ 展开详情并查看 Observation、Owner Interpretation、Safety、来源与关联项
→ 选择编辑或删除
→ 编辑后相关派生数据标记 stale / 可重算
→ 删除前明确影响范围并二次确认
```

用户不能因切换页面、加载失败或错误重试而意外改变原记录。历史 Safety Check 不得被普通内容编辑静默改写。

### 4.4 安排并完成复评

```text
Episode 详情安排复评
→ Today 在到期或逾期时显示待办
→ 用户查看原记录
→ 选择改善 / 持续 / 加重 / 已消失 / 新情况
→ 写下本次 Observation 与可选 Interpretation
→ 再次完成人工 Safety Check
→ 保存为新 Episode，并与原记录双向关联
```

取消待办不删除原 Episode；完成复评不会覆盖第一次记录。

### 4.5 建立观察计划与个体基线

```text
Today 创建一段观察
→ 定义目标与至少一个观察项
→ 后续 Episode 选择关联该计划
→ 完成或取消计划
→ Us 查看按窗口计算的 Baseline
→ 查看样本量、状态、指标、趋势条件与原始来源
```

当样本不足或没有数据时，产品只显示 `INSUFFICIENT_DATA` 或 `EMPTY` 的用户语言，不推测趋势。编辑或删除来源后，旧快照不得继续冒充最新结果。

### 4.6 长期记忆控制

```text
系统产生符合规则的记忆候选
→ 用户查看候选陈述、证据、不确定性与来源版本
→ 用户主动选择纳入或忽略
→ 已纳入内容可撤回
→ 撤回只改变长期记忆状态，不修改原始 Episode
```

若 AI Understanding 未通过资格门禁，则不向真实用户产生新的 AI 记忆候选；首发不以“自动懂你的宠物”作为完成条件。

### 4.7 数据退出

```text
设置 / 数据与隐私
→ 查看数据处理说明
→ 请求导出，获得可读且可携带的数据副本
或
→ 请求删除账号
→ 明确删除范围与不可逆后果
→ 二次确认
→ 在承诺时限内删除或匿名化，并告知完成结果
```

## 5. 首发信息架构与页面职责

主导航继续冻结为四个一级入口：

| 页面 | 唯一主职责 | 不承担的职责 |
|---|---|---|
| Today / 今天 | 呈现当前宠物、到期复评、进行中的观察计划和“开始记录” | 不做综合评分仪表盘 |
| Record / 记录 | 创建一次结构化 Episode 并完成 Safety Check | 不直接输出诊断或无证据的答案 |
| Timeline / 足迹 | 查找、展开、修订、删除和追溯历史记录 | 不把 Timeline 卡片简化成情绪标签流 |
| Us / 我们 | 宠物档案、长期记忆、Baseline、记录原则与数据控制入口 | 不虚构完整 Owner/Relationship 模型 |

账号、隐私、导出、删除、宠物切换属于全局能力，不新增第五个业务 Tab。任何页面不得出现无真实目标的按钮或重复入口。

## 6. 明确非目标

以下内容不属于首发，即使已有架构边界或实验实现也不得对外描述为已提供：

1. 疾病诊断、心理诊断、急诊分诊、治疗、处方与用药建议；
2. “爱主人指数”“焦虑百分比”、单一情绪标签或其他伪精确评分；
3. 上传图片、视频或音频后自动识别行为；
4. 安全 RAG、自动查询兽医知识库或基于知识库的个体医疗判断；
5. Agent 自动行动、自动联系兽医、自动改变记录或自动执行计划；
6. 任何未经用户确认的 AI 内容进入长期记忆或 Baseline；
7. Pet↔Pet 关系推断、多宠互动分析或“嫉妒/不合”等长期标签；
8. 完整 Owner Model、人格画像、依恋类型或对主人的心理分析；
9. 兽医端、机构端、家庭多人实时协作与角色权限系统；
10. 社区、公开内容流、排行榜、连续打卡压力与关系游戏化；
11. 电商、保险、问诊交易、广告和个性化商品推荐；
12. 对宠物健康结果、行为改善结果或人与宠物关系改善作保证；
13. 原生 iOS/Android 应用、穿戴设备或智能家居集成；首发以响应式 Web 为唯一客户端；
14. 离线优先与跨设备实时协作；网络失败时必须保护输入，但不承诺完整离线使用。

## 7. 首发验收条件

### 7.1 产品闭环验收

以下场景必须全部通过，任一失败则不能邀请真实用户：

- 新用户可注册/登录、理解边界、创建宠物，并在无历史数据时看到真实空状态；
- 用户可在 3 分钟内完成一条最小记录：原始描述、至少一条 Observation 和 Safety Check；
- Owner Interpretation 可以为空；填写时与 Observation 在输入、保存、详情和编辑中始终分离；
- `NORMAL` 记录可保存并立即在 Timeline 找到；保存失败不清空输入，且提供重试；
- 危险信号触发时，页面持续显示联系兽医提示，且服务端与客户端都不能发起模型解释；
- 用户可从原 Episode 安排复评，在 Today 完成复评，并从新旧记录互相追溯；
- 用户可创建、完成和取消观察计划，取消不会删除已关联记录；
- 用户可编辑 Episode；依赖它的分析、记忆或 Baseline 会正确显示 stale 或经重算更新；
- 用户删除 Episode 前能看见影响范围；确认后该记录不再出现在 Timeline，关联数据保持一致；
- Baseline 在空数据、样本不足、可计算和来源失效四种情况下均给出真实状态；
- 用户能查看 Baseline 的样本量、时间窗口、算法版本或面向用户的版本说明，并下钻到来源；
- 用户可明确纳入和撤回长期记忆，操作不改写原始记录；
- 多宠用户切换当前宠物后，Today、Record、Timeline 与 Us 不串数据；
- 用户可从产品内找到隐私说明、数据导出和账号删除入口，并完成相应请求。

### 7.2 安全与内容验收

- 所有关键路径统一表达“Relapaw 不诊断、不替代兽医”；
- Safety 提示不能只依赖会消失的 toast，也不能被品牌插画或营销文案弱化；
- 对 `NEED_MORE_INFO` 与 `ESCALATE_TO_VET` 的处理有服务端自动测试和人工验收证据；
- 任何展示给用户的派生陈述都能追溯来源，并区分事实、用户理解、系统计算和模型候选；
- `NOT_QUALIFIED` 模型组合在生产默认配置、界面入口和宣传材料中均不得被包装为可用能力；
- 不使用宠物第一人称替模型表达确定感受，不使用诊断性、治疗性或保证性语言。

### 7.3 隐私、账号与运营验收

- 每个 API 读取和写入都按已登录用户隔离，无法通过修改 ID 访问他人宠物或记录；
- 生产环境使用 HTTPS、服务端 Secret 管理、最小化日志和数据库备份；日志不记录 API Key 或完整敏感正文；
- 服务条款、隐私说明、数据保存规则、导出与删除时限经过发布前审核；
- 邀请、反馈、故障响应和安全事件升级均有明确责任人及可执行流程；
- 演示数据、测试数据与真实用户数据环境隔离；生产问题排查不依赖复制真实正文到非生产环境。

### 7.4 体验与可靠性验收

- 支持当前两个主要 Chromium 浏览器版本的桌面与移动宽度；不出现底栏遮挡、横向溢出或关键操作不可见；
- 所有关键操作可仅用键盘完成，焦点清晰，表单有可读标签，状态消息可被辅助技术感知；
- `prefers-reduced-motion` 下无非必要位移；Safety、Observation 与 Interpretation 不只用颜色区分；
- 核心读取页面覆盖 loading、content、empty、error/retry；关键写入覆盖 submitting、success、failure；
- 数据库迁移可从空库执行，备份恢复演练通过；前后端健康检查、结构化日志和错误监控可用；
- Release Candidate 的自动测试、构建、迁移、浏览器核心路径和人工验收全部通过，无未关闭的 P0/P1 缺陷。

## 8. Beta 观测指标与继续/停止条件

这些指标用于判断首发假设，不用于评价宠物或主人：

| 目标 | 指标定义 | 首轮判断参考 |
|---|---|---|
| 用户理解双镜头 | 首条有效 Episode 同时保留 Observation 且没有把 Interpretation 写入事实字段的用户占比 | 访谈与记录抽样确认多数用户无需人工纠正 |
| 形成复评闭环 | 创建过 Episode 的用户中，至少完成一次复评的占比 | 能证明复评不是只有团队自己使用的功能 |
| 建立长期价值 | 连续两周内至少在两个不同日期记录的用户占比 | 能区分长期工具与一次性咨询入口 |
| 安全门禁可靠 | 非 NORMAL 场景中的模型调用次数 | 必须为 0 |
| 数据可信 | 跨用户数据泄漏、不可解释丢失或无法恢复的严重事件数 | 必须为 0 |
| 来源可理解 | 用户能否从 Baseline 或记忆返回原始来源 | 可用性测试中全部关键任务可完成 |

首轮 Beta 不预设虚假的增长目标。若出现跨用户数据访问、Safety 绕过、不可恢复的数据丢失或诊断性输出，立即暂停新增邀请，完成事件处理和回归后再恢复。

## 9. 发布决策门禁

只有以下条件全部满足，版本才可从内部演示进入真实用户受邀 Beta：

```text
本契约由产品负责人确认
→ 账号、授权、隐私、导出与删除达到 P0
→ 核心流程与安全验收全部通过
→ 生产部署、监控、备份恢复和环境隔离通过
→ Release Candidate 无未关闭 P0/P1
→ 对外文案与实际能力逐项一致
→ 指定 Beta 负责人、支持渠道和暂停机制
→ 才能发送第一批真实用户邀请
```

通过首发门禁不等于允许公开发布。扩大邀请、开放注册、引入 AI Understanding 或进入应用商店，均需单独的范围与风险评审。

## 10. 变更控制

本文件冻结首发产品边界。任何新增 P0、删除既有 P0、改变核心流程、将非目标提前到首发，或启用 AI Understanding，都必须：

1. 写明变更原因和用户证据；
2. 标明对安全、隐私、数据模型、交付时间和现有验收的影响；
3. 更新本文件版本与日期；
4. 获得产品负责人明确确认；
5. 再进入架构与实现。

视觉调整、文案澄清和不改变用户结果的小修复不构成范围变更，但仍不得弱化 Safety、Evidence、Uncertainty、人工决定或 `NOT_QUALIFIED` 结论。
